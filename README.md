# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산을 반복문으로 직접 구현해 십자가(Cross)/X 패턴을 판별하는 콘솔 애플리케이션입니다.

## 실행 방법

```
python main.py
```

실행 후 모드를 선택합니다.

- `1` : 사용자 입력(3×3) — 필터 A, B와 패턴을 콘솔에서 한 줄씩(공백 구분) 입력받아 판정합니다.
- `2` : data.json 분석 — 같은 폴더의 `data.json`(5×5, 13×13, 25×25 필터/패턴)을 읽어 일괄 판정합니다.

`data.json`은 `main.py`와 같은 디렉터리에 있어야 하며, 경로는 `DATA_JSON_PATH` 상수로 지정되어 있습니다.

**파일 구성**: 기능별로 모듈을 나눴습니다. 실행은 `main.py`만 하면 되지만, 아래 5개 파일이 전부 같은 폴더에 있어야 `import`가 성공합니다.

| 파일 | 역할 |
|---|---|
| `core.py` | 데이터 구조(2D/1D), MAC 연산(2D/1D), 라벨 정규화, 점수 판정 |
| `io_console.py` | 모드 1 콘솔 입력 + 검증 |
| `json_mode.py` | 모드 2: data.json 로드, 스키마 검증, 케이스 판정, 결과 요약 |
| `perf.py` | 성능 측정, 2D/1D 비교 (보너스 1) |
| `patterns.py` | 패턴 생성기 (보너스 2) |
| `main.py` | 진입점, 모드 1/2 실행 흐름 |

## 구현 요약

- **데이터 구조**: n×n 패턴/필터를 파이썬 리스트의 리스트(list of list)로 표현하고, `core.py`의 `create_grid` / `get_cell` / `set_cell`로 생성·조회·저장합니다.
- **MAC 연산**: `mac_operation`이 이중 for문으로 `pattern[r][c] * filter[r][c]`를 모두 더해 유사도 점수를 계산합니다. NumPy 등 외부 라이브러리는 사용하지 않았습니다.
- **라벨 정규화**: `normalize_label`이 `'+' / 'cross'` → `Cross`, `'x'` → `X`로 변환합니다. data.json의 `expected` 값과 필터 키(`cross`/`x`) 모두 이 함수를 거쳐 표준 라벨로 통일한 뒤 비교합니다.
- **동점 처리 정책**: `judge_scores`는 `abs(score_a - score_b) < 1e-9`(EPSILON)이면 `UNDECIDED`를 반환합니다. 부동소수점 연산은 미세한 오차가 발생할 수 있으므로, `==` 대신 허용오차 기반 비교를 사용했습니다.
- **모드 2 예외 처리**: `analyze_json_patterns`는 케이스 키 형식 오류, 필터 없음, 패턴/필터 크기 불일치, 스키마 누락, 기타 예외를 각각 `try/except`와 조건 분기로 잡아 해당 케이스만 FAIL 처리하고 `continue`합니다. 어떤 경우에도 프로그램 전체가 중단되지 않습니다.

## 핵심 개념

**부동소수점 오차와 epsilon 비교**
컴퓨터는 0.9 같은 소수를 2진수로 정확히 표현하지 못해서 계산 중 아주 작은 오차가 생길 수 있습니다(예: `0.9`와 `0.8999999999999999`). 이걸 `==`로 비교하면 실제로는 같은 값인데도 다르다고 잘못 판단할 수 있습니다. 그래서 `judge_scores`는 `abs(score_a - score_b) < 1e-9`처럼 아주 작은 허용 오차(epsilon)보다 차이가 작으면 "동점(UNDECIDED)"으로 처리합니다.

**메모리 레이아웃과 1차원 배열 (보너스 관련)**
2차원 리스트(`grid[row][col]`)는 리스트 안에 리스트가 들어있는 구조라 값들이 메모리 여러 곳에 흩어질 수 있습니다. 반면 1차원 리스트(`grid[row*N + col]`)는 값들이 메모리에 한 줄로 이어져 있어서 CPU가 더 빠르게 읽어올 수 있습니다(캐시 지역성). 보너스 과제에서 2차원 배열을 1차원으로 바꿔 성능을 비교하는 이유가 여기에 있습니다.

**직렬 처리 vs 병렬 처리 (NPU가 필요한 이유)**
CPU는 명령어를 하나씩 순서대로 처리하는 데 최적화돼 있습니다. 하지만 MAC 연산은 각 칸의 계산이 서로 독립적이라(한 칸의 곱셈이 다른 칸 결과에 영향을 주지 않음) 여러 칸을 동시에 계산해도 문제가 없습니다. NPU/GPU는 이런 독립적인 단순 연산을 수천 개씩 한꺼번에(병렬로) 처리하도록 만든 하드웨어라서, MAC 연산이 아주 많은 AI 모델에 특히 잘 맞습니다.

**데이터 정규화(라벨 표준화)**
`data.json`에는 같은 의미를 다르게 표기한 값들이 섞여 있습니다(`expected`는 `'+'`/`'x'`, 필터 키는 `'cross'`/`'x'`). 비교하기 전에 이런 값들을 하나의 기준(`Cross`/`X`)으로 통일하는 과정이 정규화입니다. 정규화를 하지 않으면 의미는 같은데 표기만 달라서 잘못 비교되는 버그가 생길 수 있습니다. `normalize_label` 함수가 이 역할을 합니다.

## 결과 리포트

### FAIL 케이스 원인 분석

`data.json` 분석 결과, 6개 케이스의 판정은 다음과 같습니다.

| 케이스 | 크기 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|---|
| size_5_1 | 5×5 | 0.9 | 0.8999999999999999 | UNDECIDED | X | **FAIL** |
| size_5_2 | 5×5 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 13×13 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 13×13 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | **FAIL** |
| size_25_1 | 25×25 | 4.9 | 4.899999999999999 | UNDECIDED | X | **FAIL** |
| size_25_2 | 25×25 | 52.9 | 0.1 | Cross | Cross | PASS |

**총 6개 / 통과 3개 / 실패 3개**

FAIL 3건(`size_5_1`, `size_13_2`, `size_25_1`)은 표에서 보이듯 Cross/X 점수 차이가 `1e-9`(EPSILON) 미만으로, 원인이 세 건 모두 동일합니다.

1. 점수 차이가 EPSILON보다 작아 `judge_scores`가 `UNDECIDED`를 반환했습니다 (예: `size_13_2`는 `7.499999999999997` vs `7.5`).
2. 이 차이는 실제 값의 차이가 아니라 `float` 연산 과정에서 생긴 부동소수점 오차 수준이며, 사람이 보기엔 사실상 같은 값입니다.
3. 과제의 판정 규칙상 `UNDECIDED`는 FAIL로 집계되므로, 세 케이스 모두 FAIL 처리되는 것이 올바른 동작입니다.
4. 즉 원인은 "데이터/스키마 문제"도 "로직 버그"도 아니라, 세 번째 범주인 **"수치 비교 정책(동점 처리 규칙)"** 에 의한 정상적인 결과입니다.
5. epsilon을 더 크게(예: `1e-6`) 잡으면 세 케이스 모두 PASS로 뒤집힐 수 있음을 확인했고, 이는 epsilon 값 자체가 최종 판정을 직접 좌우한다는 것을 보여줍니다.

PASS 3건(`size_5_2`, `size_13_1`, `size_25_2`)은 표에서 보듯 두 점수 차이가 충분히 커서(0.1~14 수준) 명확하게 판정되었고, 정규화된 `expected`와도 일치했습니다.

스키마 문제(패턴/필터 크기 불일치, 필터 누락 등)로 인한 FAIL은 이번 `data.json`에서는 발생하지 않았습니다. `filters`의 `size_5/13/25`와 `patterns`의 `size_N_*` 키가 서로 정확히 대응하도록 데이터가 구성되어 있었기 때문입니다. 이 검증 로직 자체는 패턴 크기를 일부러 깨뜨리거나 존재하지 않는 `size_99` 필터를 요구하는 케이스를 임의로 추가해 별도로 테스트했고, 두 경우 모두 프로그램이 죽지 않고 해당 케이스만 정확히 FAIL 처리되는 것을 확인했습니다.

### 시간 복잡도 분석 (O(N²))

1. `mac_operation`은 n×n 격자에 대해 이중 for문(행 n번 × 열 n번)을 돌며 위치마다 곱셈 1번, 덧셈 1번을 수행합니다.
2. 격자 전체를 훑으려면 이 연산을 정확히 `n²`번 반복해야 하므로, 이론적 시간복잡도는 **O(N²)** 입니다.
3. 실제 측정 결과(각 크기마다 MAC 연산 10회 반복 후 평균, I/O 제외)는 다음과 같습니다.

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.005 | 9 |
| 5×5 | 0.011 | 25 |
| 13×13 | 0.053 | 169 |
| 25×25 | 0.186 | 625 |

4. 연산 횟수(N²) 기준으로 5×5→13×13 구간은 `(13/5)² ≈ 6.76`배, 13×13→25×25 구간은 `(25/13)² ≈ 3.70`배 늘어납니다.
5. 측정 시간도 각각 약 4.8배(0.011→0.053), 3.5배(0.053→0.186) 늘어나 N²에 비례하는 O(N²) 경향과 대체로 일치합니다.
6. 다만 3×3→5×5 구간은 연산 횟수가 2.78배 늘었는데 측정 시간은 2.2배만 늘어, 이론값보다 증가 폭이 작게 나타났습니다.
7. 이는 크기가 아주 작을 때는 실제 곱셈·덧셈 연산 시간보다 함수 호출, 반복문 초기화 같은 고정 오버헤드의 비중이 상대적으로 크기 때문입니다.
8. 격자 크기가 커질수록 이 고정 오버헤드의 비중은 작아지고, 실제 연산량(N²)이 전체 시간을 지배하게 되어 25×25처럼 큰 입력에서 이론적 O(N²) 경향에 더 가까워집니다.
9. 정리하면, 측정치는 "연산 횟수가 N²에 비례해 늘어나므로 시간도 N²에 비례해 늘어난다"는 이론과 큰 틀에서 일치하며, 작은 N에서의 오차는 알고리즘 자체가 아니라 측정/실행 환경의 고정 오버헤드에서 기인합니다.

## 보너스 과제

### 1) 시뮬레이터 최적화 (2차원 → 1차원 배열)

`create_grid_1d` / `get_cell_1d` / `set_cell_1d` / `mac_operation_1d`를 추가해, 기존 `grid[row][col]` 방식 대신 `grid[row*n+col]`로 인덱싱하는 1차원 버전을 구현했습니다. 동일한 입력, 동일한 반복 횟수(10회)로 2D/1D 버전을 각각 측정해 비교한 결과는 다음과 같습니다.

| 크기 | 2D 평균(ms) | 1D 평균(ms) | 배율(2D/1D) |
|---|---|---|---|
| 3×3 | 0.006 | 0.004 | 1.55x |
| 5×5 | 0.012 | 0.006 | 1.78x |
| 13×13 | 0.061 | 0.039 | 1.54x |
| 25×25 | 0.198 | 0.150 | 1.32x |

모든 크기에서 1차원 버전이 더 빠르게 측정됐습니다. 2차원 리스트는 `grid[row][col]`처럼 인덱싱을 두 단계(바깥 리스트 → 안쪽 리스트) 거쳐야 하고 값들이 메모리에 흩어져 있을 수 있는 반면, 1차원 리스트는 인덱싱이 한 단계(`grid[i]`)뿐이고 값들이 메모리에 연속으로 이어져 있어 CPU 캐시를 더 잘 활용하기 때문입니다.

### 2) 패턴 생성기

`generate_cross(n)` / `generate_x(n)` 함수를 추가해, 크기 N만 주면 N×N 십자가/X 패턴을 자동으로 생성하도록 구현했습니다. 두 함수 모두 `create_grid`와 같은 list-of-list 형식을 반환하므로, `mac_operation`이나 `read_grid_from_console`이 만드는 데이터와 완전히 같은 형태이며 그대로 바꿔 쓸 수 있습니다. `run_mode2`의 3×3 성능 측정에서 기존에 하드코딩했던 3×3 십자가/X 값을 이 생성기 호출(`generate_cross(3)`, `generate_x(3)`)로 대체해 실제로 재활용하고 있으며, 같은 이유로 모드 1의 필터/패턴 대신 사용할 수도 있습니다.
